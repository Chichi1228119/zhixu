# 代码注解：从请求到权限、来源和恢复

本页解释关键模块的责任和不能省略的边界，供维护者阅读与修改。运行步骤见 [完整使用指南](user-guide.md)，接口字段见 [API 文档](api.md)。

## 入口与数据路径

[`app/cli.py`](../app/cli.py) 的 `main()` 解析启动、初始化、密码恢复和备份命令。`serve` 只允许回环监听；企业模式是显式选项。密码通过 `getpass` 输入，而不是命令行参数，避免进入进程参数和 shell 历史。

[`app/paths.py`](../app/paths.py) 将安装资源与运行数据分开：静态页面、示例和题集从包内读取，数据库、配置、模型和报告写到指定的可写目录。不能把数据库写到 `site-packages`，也不能让客户端传入服务器目录。

[`app/main.py`](../app/main.py) 的 `create_app()` 组装 HTTP 服务。个人模式保留单库；企业模式先建立权限边界，不自动迁移或共享旧个人库。参数校验错误会去掉 Pydantic 的原始输入，防止密码/key 在 422 响应中回显。

## 企业请求为何要先经过边界

[`app/enterprise.py`](../app/enterprise.py) 的 `authorize()` 在业务处理前执行：

1. 根据 Cookie 的随机令牌查服务端会话。数据库只存令牌摘要；过期、停用和已吊销令牌不被接受。
2. 对修改请求校验会话 CSRF；模型、账号和全局评测等接口还要求系统管理员。
3. 对资料接口验证空间 ID 格式与成员关系，检查 viewer 是否尝试修改。
4. 验证成功才选择服务器生成 ID 对应的独立知识库，并放入当前请求状态。

权限不能仅靠前端隐藏按钮，不能根据客户端提交的角色决定，也不能先检索全库再在回答后过滤。不同空间的去重、资料读取、索引和问答都在各自的 `KnowledgeService` 内完成，避免跨空间信息进入候选来源。

[`app/origins.py`](../app/origins.py) 比较 scheme、hostname 和有效端口；只比较主机名会漏掉 HTTP/HTTPS 或端口差异。Host 白名单、Origin 与 CSRF 是不同检查，不能互相替代。

## 身份、并发与审计

[`app/identity.py`](../app/identity.py) 使用维护的 `argon2-cffi`，不自行设计密码算法。随机会话、失败限速、成员与审计存于控制库，SQL 使用参数绑定。用户名规范化和唯一约束在库层生效。

最后管理员保护、授权变更和密码变更采用写事务；密码校验后的写入还要重新核对当前密码哈希，避免并发重置被旧请求覆盖。密码修改/重置和账号停用会删除该用户的全部会话。成员角色在每次请求中重新查询，因此已登录也不能保留被撤销的空间访问。

Argon2 计算设置进程内并发上限，登录失败记录持久化。它们不能代替部署侧限流、网络控制或 MFA。审计记录 actor/action/workspace/target/outcome/request ID，不存问题、文档或秘密；本机数据库管理员仍能修改审计，不能宣传成防篡改日志。

## 导入、去重与检索

[`app/ingestion.py`](../app/ingestion.py) 负责有预算的提取与位置保留，长段按 900 字符窗口、120 字符重叠切分。PDF 页码、文本段落和 DOCX 表格位置不应混为同一种坐标。

[`app/docx_ingestion.py`](../app/docx_ingestion.py) 先检查 ZIP 预算和危险结构，再通过 `python-docx` 提取。表格遍历物理单元格，而不是展开 `row.cells`，否则恶意 `gridSpan` 能将一个单元格放大成大量重复文字。文字、XML 节点和嵌套预算在提取时执行；这些预算仍不是进程隔离或硬超时。

[`app/service.py`](../app/service.py) 的 `import_document()` 先校验解析，再按字节 SHA256 去重。导入/删除后必须使内存索引失效。`store.py` 只负责参数化 SQLite 生命周期，不接受任意 SQL 或外部文件路径。

[`app/retrieval.py`](../app/retrieval.py) 提供 BM25、TF-IDF 与 RRF 排序。候选门限会影响所有字面策略；不能只根据融合名称宣称更好。`semantic.py` 是独立可选 BGE 分支，固定余弦门限不是可信概率，也不自动保证回答属性充分。

## 模型设置和回答校验

[`app/model_settings.py`](../app/model_settings.py) 保存服务端配置，读取时脱敏。保存使用独占临时文件、刷新与原子替换；写盘失败不能让内存配置悄悄变成另一套。只有目标地址不变时才允许留空沿用 key，防止旧 key 被转移到新服务。环境管理时网页只读。

[`app/provider.py`](../app/provider.py) 仅在用户选择生成、配置可用且有来源时发送请求。它要求 JSON 对象、合法状态和真实来源编号，正文引用集合要与 `source_ids` 一致，并拒绝只有编号的空答案。资料不足可返回无引用的明确拒答。

这些检查只证明响应结构和编号符合约定，不证明事实正确。生成失败时，`main.py` 保留真实原文摘录并加 `generation_error` 与警告，不能把摘录伪装成成功生成。日志和错误响应不得包含服务响应中的秘密或请求头 key。

## 备份恢复为何不直接解压

[`app/backup.py`](../app/backup.py) 只处理允许清单中的数据库和设置，用 SQLite backup API 收集快照。ZIP 载荷有大小、数量、路径、重复成员和符号链接检查；恢复先在同文件系统 staging 验证清单、SHA256 和数据库完整性，最后发布到新的空目录。

控制库会剥离活动会话，旧归档恢复也作同样处理，避免原 Cookie 复活。返回的 manifest 描述归档载荷；若旧载荷带会话，恢复后的控制库字节会因剥离而改变。不要把哈希校验说成数字签名、加密或来源认证，也不要把逐库一致说成跨库原子快照。

## 修改代码后的验证

先写能复现问题的测试，确认失败，再做最小修复。重点测试未登录、跨空间对象 ID、viewer 修改、CSRF/Origin、停用与密码吊销、ZIP 攻击、校验失败和恢复不覆盖数据。完整命令见 [贡献指南](../CONTRIBUTING.md)。

`scripts/verify_wheel.py` 验证安装后的包，而不是从源码导入；它在临时目录启动真实 HTTP 进程，用服务端实际 worker 的退出流程清理。Windows venv launcher PID 可能不同于真正的 Python worker，不能只检查或终止外层 shim。
